# CODING_STANDARDS

Project: AI Infrastructure

Document ID: DOC-0001.10

Version: 1.0

Status: Active

# 1. Purpose

Данный документ определяет единые стандарты разработки AI Infrastructure.

Все изменения кода, документации и архитектуры должны соответствовать данным правилам.

---

# 2. Python

- Python 3.11+
- Следовать PEP 8.
- Использовать type hints для всех публичных функций.
- Не использовать глобальные переменные без необходимости.
- Один модуль — одна ответственность.
- Предпочитать явный код неявному.

---

# 3. Project Structure

Каждый модуль располагается в собственной директории.

Пример:

```text
src/
    hf_client/
    model_registry/
    download_worker/
    queue_manager/
```

Каждый модуль должен иметь понятную и минимально необходимую структуру.

---

# 4. Imports

Порядок импортов:

1. Стандартная библиотека.
2. Внешние зависимости.
3. Внутренние модули проекта.

Импорты должны быть сгруппированы и разделены пустой строкой.

---

# 5. Functions

Каждая функция должна выполнять одну логическую задачу.

Рекомендуется:

- небольшие функции;
- понятные имена;
- минимум побочных эффектов;
- минимальная вложенность.

---

# 6. Naming

## Files

`snake_case.py`

## Functions

`snake_case()`

## Classes

`PascalCase`

## Constants

`UPPER_CASE`

## Variables

`snake_case`

---

# 7. Logging

Не использовать `print()` в рабочем коде.

Использовать модуль `logging`.

`print()` допускается только для временной локальной диагностики и должен быть удалён перед завершением HF.

---

# 8. Docker

Каждый сервис имеет собственный `Dockerfile`.

Все сервисы запускаются через `docker compose`.

Работоспособность нового функционала проверяется внутри Docker Compose.

---

# 9. Documentation

После завершения каждого HF необходимо обновить документацию проекта.

Минимальный набор:

- CURRENT_STATUS.md
- ROADMAP.md (при необходимости)
- MODULE_INDEX.md (если изменилась архитектура)
- API_INDEX.md (если изменились публичные интерфейсы)
- DECISIONS.md (если принято новое архитектурное решение)
- CHANGELOG.md

Документация является обязательной частью проекта.

---

# 10. Definition of Done (DoD)

HF считается завершённым только после выполнения всех пунктов.

## Code Review

- Проверены все изменённые файлы.
- Исправлены замечания.
- Удалён временный диагностический код.

---

## Functional Testing

- Выполнены локальные проверки.
- Проверены основные сценарии.
- Проверены сценарии ошибок (при необходимости).

---

## Docker Integration Testing

Каждый новый функционал проходит интеграционную проверку через Docker Compose.

Проверяется:

- запуск сервисов;
- взаимодействие сервисов;
- работа Docker volumes;
- работа Registry;
- работа архивного хранилища.

HF не может считаться завершённым без успешного интеграционного тестирования.

---

## Documentation Review

Обновлены все необходимые документы проекта.

---

## Completion

Только после выполнения всех пунктов HF получает статус:

**COMPLETED**

---

# 11. Debugging

При поиске ошибок допускается использование временного диагностического кода.

Правила:

- диагностический код не коммитится;
- после завершения проверки полностью удаляется;
- рабочая версия проекта не должна содержать временных `print()` и иных отладочных конструкций.

---

# 12. Engineering Principles

При разработке необходимо придерживаться следующих принципов:

- Documentation First
- Infrastructure First
- Preserve Originals
- Extend, Never Replace
- Backward Compatibility
- Modular Architecture

Эти принципы являются обязательными для всех Runtime-проектов AI Infrastructure.


# 13. Структура проекта

# Пути к файлам

Все пути внутри проекта должны вычисляться относительно корня проекта.

Запрещается использовать абсолютные пути, например:

- C:\Users\...
- D:\OneDrive\...
- E:\Projects\...

Используются только вычисляемые пути, например:

PROJECT_ROOT = Path(__file__).resolve().parent.parent

или другой эквивалентный способ определения корня проекта.

Проект должен корректно работать независимо от расположения репозитория на файловой системе.
